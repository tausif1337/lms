Part OneOrientation

What the project is, what it is built from, where everything lives, and what actually happens when you click something.

1. What this project is

Two applications that talk to each other over JSON, plus one database behind them.

The backend is a Django 5.2 project with Django REST Framework on top. It owns the database, issues the JWT tokens, and holds every rule about who is allowed to change what. The frontend is a React 19 single-page application built by Vite and styled with Tailwind. It has fifteen screens and no mock data anywhere: if the API is down, the pages say so rather than inventing rows.

The domain is a small online-course provider. Nine tables model it: a Profile beside each Django User, then Teacher, Student, Course, Lesson, Assignment, Enrollment, Submission and Results. Eight of those get a full CRUD screen in the browser.

1.1 The two things that surprise people first

You sign in with a phone number, not a username. The login view looks the caller up by Profile.phone, which is a unique column, and then checks the password against the User it hangs off. The username still exists — it is how an admin finds you — but it is not a credential.

There is no public sign-up. POST /api/register/ is guarded by IsAdmin, which refuses every method including GET. An admin creates accounts from the Accounts screen inside the app and picks the role at the same time. Anonymous callers get 401; signed-in teachers and students get 403.

1.2 The three rules the codebase sticks to

  1. The API is what enforces permissions. The frontend hides buttons that would not work, but that is a courtesy to the reader, not a control. Every write is checked again on the server by a permission class.
  2. Every request the frontend makes lives in src/api.js. Nothing else in the React app calls fetch. One file to read to know the whole surface the browser touches.
  3. The eight table pages are the same page eight times. Same hook, same components, different columns and different field names. Read pages/Students.jsx once and you have read all eight.

3.1 The one confusing name

6. Step 1 — The database

Create the database and a user for it. These three names are the defaults compiled into backend/lms/settings.py, so matching them means you can skip the environment variables entirely.

CREATE DATABASE lms_db CHARACTER SET utf8mb4;
CREATE USER 'lms_user'@'127.0.0.1' IDENTIFIED BY 'lms_user_pw';
GRANT ALL PRIVILEGES ON lms_db.* TO 'lms_user'@'127.0.0.1';

In one line from a shell:

mysql -u root -e "
  CREATE DATABASE lms_db CHARACTER SET utf8mb4;
  CREATE USER 'lms_user'@'127.0.0.1' IDENTIFIED BY 'lms_user_pw';
  GRANT ALL PRIVILEGES ON lms_db.* TO 'lms_user'@'127.0.0.1';
"

127.0.0.1 and localhost are different hosts to MySQL's grant system: one means TCP, the other means the unix socket. The settings file uses 127.0.0.1, so grant to that. Granting to 'lms_user'@'localhost' instead is the most common reason for Access denied on the first migrate.

7. Step 2 — The backend

cd backend
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt

python manage.py migrate
python manage.py runserver 8001

Four migrations run, in order: the three original models, then the other six, then Profile.role, then the data migration that promotes any pre-existing account to admin. On an empty database that last one updates nothing.

Two addresses are now live:

AddressWhat
http://127.0.0.1:8001/api/The JSON API. A browser hitting it gets DRF's browsable pages.
http://127.0.0.1:8001/admin/Django admin. Nine models registered; this is where roles are changed.

Port 8001, not 8000. The frontend's default VITE_API_URL, the smoke test's default LMS_API, and the CORS list all assume 8001. Running runserver with no argument gives you 8000 and nothing will connect.

7.1 If there is no admin account yet

python manage.py createsuperuser

A superuser has no Profile row, and therefore no role column to read. role_of() in permissions.py checks user.is_superuser first and returns admin, so createsuperuser is always a way back into a locked-out system.

8. Step 3 — Seeding data

python manage.py seed_data

This fills the database with a realistic amount of realistic-looking data — around 180 students, two dozen courses, several thousand submissions and a few thousand grades — and guarantees the three demo logins. It takes a few seconds and prints a table of totals when it finishes.

8.2 Why running it twice is safe

Every "does this row exist yet" decision is derived from the ids involved rather than drawn from a random stream. A helper called dice() hashes the inputs with zlib.crc32 and takes the result modulo 100, so the same question gives the same answer in this process and in the next one. A student who had handed in four of six assignments still has four of six after a second run. Rows are found by a stable key first — a person by email, a course by title, a lesson by title within its course — so nothing is duplicated either. Full detail in chapter 23.

--fresh deletes all course data — every teacher, student, course, lesson, assignment, enrollment, submission and result in the database, seeded or not — plus every non-superuser account whose email ends in @ostad.example.com or @student.example.com. Superusers survive. Do not point it at anything you care about.

9. Step 4 — The frontend

cd frontend
npm install
npm run dev

Vite serves on http://localhost:5180. That port is set explicitly in frontend/vite.config.js because 5173–5175, Vite's own defaults, were already taken by other projects on the author's machine. If 5180 is busy too, Vite quietly takes the next free port and prints which one.

If Vite moves to another port, add that origin to CORS_ALLOWED_ORIGINS in backend/lms/settings.py or every request will be blocked by the browser before it leaves. The list currently allows 5180 and 5173, on both localhost and 127.0.0.1.

9.1 Pointing it at a different backend

cp .env.example .env.local
# then edit:
VITE_API_URL=http://127.0.0.1:8001/api

Two things about that variable. It must start with VITE_ — Vite only exposes those to the browser bundle. And it must end in /api, because every path in src/api.js is written relative to it ("/login/", "/student/", and so on). .env.local is gitignored, which is what makes it the right place for machine-specific values.

11. Step 6 — Proving it works

With the server running in one terminal:

cd backend
python scripts/api_smoke_test.py

This is not a unit test suite. It talks HTTP to a real server with a real database, which is the only way to catch the class of problem that only appears there: a permission class wired to the wrong view, a serializer that rejects its own output, a route that was never added to urls.py.

Every check states the status code it expects, and a check that expects 403 passes only on 403. The permission rules are part of what "working" means, so a create that succeeds when it should have been refused is a failure, not a bonus. Anything the script creates it deletes on the way out — except the one account the registration check makes, because the API has no delete-user route; it says so and tells you to remove it from /admin/.

SIMPLE_JWT

SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(hours=8),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "AUTH_HEADER_TYPES": ("Bearer",),
}

The library default access lifetime is five minutes, which forces a re-login in the middle of a task. There is no refresh endpoint in this project — the refresh token is issued and handed to the browser, but nothing ever exchanges it — so the access token is widened to eight hours instead. That single fact explains several decisions in the frontend: see chapter 35.

Password validation

All four of Django's stock validators are on: UserAttributeSimilarity, MinimumLength (8), CommonPassword and NumericPassword. They are enforced in three places, all through validate_password(): account creation, self-service password change, and password reset. This is why the smoke test's "weak password refused" checks expect 400 on "12345678" — it is both too common and entirely numeric.

Password reset

FRONTEND_PASSWORD_RESET_URL = os.getenv(
    "FRONTEND_PASSWORD_RESET_URL", "http://localhost:5180/reset-password"
)
PASSWORD_RESET_TIMEOUT = 60 * 60  # 1 hour

The view appends ?uid=…&token=… to that URL and mails the result. One hour is Django's default_token_generator window, checked server-side on the way back in.

Email

The default backend is console.EmailBackend: reset mail is printed to the terminal running runserver, not sent. Everything else in the block (EMAIL_HOST, port 587, TLS on) is a Gmail SMTP configuration waiting for you to switch EMAIL_BACKEND and supply an app password.

DEFAULT_AUTO_FIELD

DEFAULT_AUTO_FIELD = 'django.db.models.BigAutoField'

The migrations were generated on Django 6, where BigAutoField is the default primary key type. Django 5.2 falls back to AutoField unless told otherwise, which would make makemigrations want to rewrite every primary key even though the columns in the database are already bigint. This one line prevents a pointless migration.

14.2 Profile

This is the join between Django's built-in User and everything this app adds. phone is unique because it is the credential — LoginView does Profile.objects.get(phone=phone) and works back to the user. role defaults to the least privileged value, so an account created by any path that forgets to set it is a student.

14.4 The four details that shape the rest of the code

1. Results.submission is one-to-one

A submission can be graded exactly once; a second attempt is a 400 from the database constraint. That is what makes ?ungraded=true possible: it maps to results__isnull=True, which is the database answering "nothing points back at this row yet". The Results page builds its dropdown from exactly that query (chapter 33).

2. Assignment points at both a course and a lesson

Redundant on paper — a lesson already knows its course — and nothing enforces that the two agree. The frontend compensates by filtering the lesson dropdown down to the chosen course's lessons, but the API would happily accept a mismatched pair.

3. Nothing links a Student row to a User login

They are two separate tables with no foreign key between them. The seeder ties them together by email as a convention, and nothing else does. This is the single most important structural fact in the project, and the reason for the odd shape of the submission permission: a student may POST a submission but not edit or delete one, because the server has no way to tell whose work it is.

4. Two auto_now_add fields

Enrollment.enrollment_date and Submission.submitted_at are set by the database on insert and cannot be supplied by the API. The seeder works around this by inserting the rows and then rewriting the dates with bulk_update, which is why seeded enrollments spread over two years instead of all landing on today.

14.5 __str__

Every model has one, and they are what the Django admin dropdowns show. A couple reach across relations — Results.__str__ reads self.submission.student.name — so listing results in the admin without select_related is one query per row. That is only the admin; the API's ResultsListCreateView does select the relations.

Three write-only fields and four rules:

  1. current_password must actually be the current one. Knowing the old password is what makes the account yours to change; without it, a borrowed browser tab would be enough to take it.
  2. The two new passwords must match.
  3. The new one must differ from the old one.
  4. The new one must pass Django's validators, given the user for the similarity check.

15.5 The password-reset pair

PasswordResetRequestSerializer is one email field. PasswordResetConfirmSerializer does the real work in validate(): match the two passwords, base64-decode the uid into a primary key, load an active user, check the token with default_token_generator, then run the password validators. 16.2 role_of(user)

def role_of(user):
    if not user or not user.is_authenticated:
        return None
    if user.is_superuser:
        return Profile.ADMIN
    profile = Profile.objects.filter(user=user).only("role").first()
    if profile is None:
        return Profile.STUDENT
    return profile.role

Four cases, in order, and each is a decision:

  • Anonymous → None, which matches no role and so is refused everywhere.
  • Superuser → admin, without looking at the database. createsuperuser is therefore always a way back into a system with no admins left.
  • No Profile row → student. The least privilege available, rather than an exception. An account made in the shell with User.objects.create_user() falls here.
  • Otherwise → whatever the column says. .only("role") keeps it to one small query.

This runs on every write request, so it is one extra query per write. Reads only pay for it on /login/ and /profile/, since SAFE_METHODS short -circuits before the lookup.

16.3 The five classes

IsAdmin

Admins only, for every method including GET. Used on registration, because accounts are handed out by an admin rather than claimed by whoever finds the URL. Message: "Only an admin can create accounts."

RoleWritePermission — the base

class RoleWritePermission(BasePermission):
    roles_that_may_write = ()

    def has_permission(self, request, view):
        if not request.user or not request.user.is_authenticated:
            return False
        if request.method in SAFE_METHODS:
            return True
        return role_of(request.user) in self.roles_that_may_write

Not authenticated → refused. GET, HEAD, OPTIONS → allowed. Anything else → the role has to be on the list. Subclasses set one tuple and one message.

AdminWrites and TeachingStaffWrites

One tuple each: (ADMIN,) and (ADMIN, TEACHER). Between them they cover seven of the eight resources.

SubmissionWrites

class SubmissionWrites(RoleWritePermission):
    roles_that_may_write = (Profile.ADMIN, Profile.TEACHER)

    def has_permission(self, request, view):
        if (request.method == "POST"
                and request.user and request.user.is_authenticated
                and role_of(request.user) == Profile.STUDENT):
            return True
        return super().has_permission(request, view)

The one asymmetric rule in the project. A student may hand work in and nothing else. The reason is structural, not a policy choice: nothing links a Student row to a login account, so on a PATCH or DELETE the server cannot tell whether the submission belongs to the caller. Handing in is the one write that is safe without that link — the worst case is a spurious row, not a tampered-with grade.

The gap that leaves: a student can POST a submission with any student id in the body, including someone else's. Closing it properly means giving Student a foreign key to User and overriding perform_create to ignore the body's value. See chapter 45.

Query-string values arrive as strings. Passing them through would be a real bug rather than a cosmetic one: ?is_active=false would filter on the non-empty string "false", which is truthy, and so would match every row. The coercion rules, in the order they are tried:

The __isnull test is checked before the relation test, and on purpose: without it, results__isnull would be seen as a relation and "true" would be parsed as an id, raising ValueError.

A value that cannot be coerced becomes a 400 naming the offending parameter, rather than a 500 out of the database driver:

{"is_active": "'maybe' is not a valid value for this filter."}

17.4 FieldFilterBackend.filter_queryset

  1. Read view.filter_fields. Not declared? Return the queryset untouched — which is why the detail routes and the auth views are unaffected by this backend running globally.
  2. For each declared parameter, read it off the query string. Missing and empty mean the same thing — the dropdown is on "Any" — so both are skipped. Filtering on "" would match nothing, which is the opposite of what the user meant.
  3. Coerce each value, collect into one dict, apply as a single queryset.filter(**conditions).
  4. Wrap that call: an unparseable date lands as a Django ValidationError here rather than in coerce(), and is turned into a 400.

There is also a get_schema_operation_parameters() so the filters would show up in a generated OpenAPI schema. Nothing in the project generates one today.

Six auth views and sixteen resource views. The resource views are almost entirely declarative: a queryset, a serializer, a permission class, and four attributes that tell the filter backends what to do.

19.1 blacklist_user_tokens(user)

tokens = OutstandingToken.objects.filter(user=user)
for token in tokens:
    BlacklistedToken.objects.get_or_create(token=token)

Called after a password change and after a password reset. It blacklists every refresh token the user has been issued. The whole body is inside a bare try/except Exception: pass, so a missing blacklist app cannot break a password change.

This does not revoke the access token already in the caller's hands. JWTs are verified by signature, not looked up in a table, so an issued access token stays valid until it expires — up to eight hours here. Both places that call this therefore also make the frontend sign the user out. That is a real mitigation, not a complete one: a token already copied out of localStorage keeps working.

23.2 The idempotency trick

def dice(*parts):
    """A stable 0-99 for a set of ids."""
    return crc32(":".join(str(p) for p in parts).encode()) % 100

This is the whole idea. Every "does this row exist yet / should this student have handed this in" decision calls dice() with the ids involved instead of drawing from a random stream. Same inputs, same answer, in this process and the next one.

Python's own hash() would not do: it is salted per process for strings, so it gives a different answer on every run. crc32 is stable across processes and machines.

The consequence: a lesson that was skipped on the first run is skipped on every run, and a student who had handed in four of six assignments still has four of six afterwards. Rows are also found by a stable key before being created — a person by email, a course by title, a lesson by title within its course — so a second run adds nothing and duplicates nothing.

23.4 The details worth copying

Working around auto_now_add

Enrollment.enrollment_date and Submission.submitted_at cannot be set on insert. So the seeder inserts with bulk_create, reads the new rows back, computes a date for each, and rewrites them with bulk_update:

Enrollment.objects.bulk_create(new_rows, batch_size=500)
fresh = list(Enrollment.objects.filter(id__in=[r.id for r in new_rows]))
for row in fresh:
    row.enrollment_date = (
        self.now - timedelta(days=5 + dice("when", row.student_id, row.course_id) * 7)
    ).date()
Enrollment.objects.bulk_update(fresh, ["enrollment_date"], batch_size=500)

Submissions get the same treatment, but placed relative to their own assignment's due date — usually a few days before it, sometimes just after:

drift = dice("drift", row.student_id, row.assignment_id) / 10.0 - 7.0
row.submitted_at = row.assignment.due_date + timedelta(days=drift)

Grades that never move

score = max(0.0, min(100.0, random.Random(submission.id).gauss(72, 15)))

A fresh Random seeded with the submission's own id — so a mark is a function of the row, not of when the seeder happened to reach it. A normal-ish distribution centred just above a pass. About 15% of eligible submissions are skipped (dice("graded", …) >= 85) so the Results page has a backlog to show, and anything submitted in the last five days is left alone entirely.

Reading assignments back from the database

_seed_submissions queries Assignment.objects.all() rather than walking the catalogue. Courses seeded by an earlier run — or by an older version of the catalogue — have assignments too, and their students should be handing work in as well. This is why a database seeded over time can hold more courses than the catalogue currently lists: the seeder tops up and never removes without --fresh.

26. api.js — every request

One file, and the only place in the app that calls fetch. Read this and you know the entire surface the browser touches.

26.1 Session storage

localStorage rather than a cookie is what makes a page refresh keep you signed in — and also what makes the token readable by any script on the origin. See chapter 44.

26.2 readError(body, response)

DRF reports failures in at least three shapes:

{"detail": "You do not have permission to perform this action."}
{"error": "Invalid phone or password"}
{"phone": ["This field is required."], "email": ["Enter a valid email address."]}

The first is DRF's own for permissions and 404s, the second is the hand-written login view, the third is any serializer rejecting a field. readError flattens all of them into one readable string — field: message per line, with non_field_errors printed bare — which is what every <Alert> in the app ends up showing. Nothing else in the frontend has to know DRF's error shapes.

26.3 request(path, options)

The single choke point. In order:

  1. Set Content-Type: application/json if there is a body.
  2. Attach Authorization: Bearer <token> unless the caller passed auth: false (login and the two reset endpoints).
  3. fetch. A network-level failure is caught and re-thrown as "Could not reach the server. Is Django running on http://127.0.0.1:8001?" — the message you see when the backend is not up.
  4. 401 handling: clear the session and dispatch a window event called lms:unauthorised, then throw "Your session has expired. Please log in again."
  5. 204 → return null. DELETE has no body to parse.
  6. Parse the text as JSON, tolerating an empty or non-JSON body.
  7. Not OK → throw new Error(readError(...)). Every page catches that and puts problem.message in an alert.

Step 4 is where the missing refresh endpoint shows up. There is nothing to retry with, so the only honest response to a rejected token is to drop the session. The event is how AuthContext hears about it without api.js having to import React.

}

everyPage()

for (let page = 1; ; page += 1) {
  const body = await request(`/${path}/${toQueryString({...params, page, page_size: 200})}`);
  if (Array.isArray(body)) return body;      // an unpaginated endpoint
  rows.push(...(body?.results ?? []));
  if (!body?.next) return rows;
}

200 is BIGGEST_PAGE, kept in step with max_page_size in pagination.py. The Array.isArray branch is defensive: an endpoint that was never paginated would answer with a bare array.

27. auth.js and AuthContext.jsx

27.1 Why they are two files

auth.js holds the context object and the useAuth() hook. AuthContext.jsx holds the provider component. They are split because Vite's fast refresh gives up on any file that mixes components with other exports — keeping the .jsx file to a single component export keeps hot reload working.

export const AuthContext = createContext(null);

export function useAuth() {
  const value = useContext(AuthContext);
  if (!value) throw new Error("useAuth must be used inside an AuthProvider");
  return value;
}

The throw turns a missing provider into a clear error at the point of use instead of a confusing null dereference three components later.

27.2 What the provider holds

const [user, setUser] = useState(() => getSavedUser());
const [isLoggedIn, setIsLoggedIn] = useState(() => Boolean(getToken()));

Both initialised lazily from localStorage, which is what makes a page refresh not sign you out. The context value is {user, isLoggedIn, logIn, logOut} and user is only ever {id, username, role} — the full account lives on the server and is fetched by the Profile page.

27.3 The two effects

Listening for a dead token

window.addEventListener("lms:unauthorised", handleUnauthorised);

That is the event api.js fires on any 401. The handler clears user and isLoggedIn, which makes ProtectedRoute redirect to /login on the next render. No import cycle between api.js and React, because the browser's event bus sits between them.

Topping up a role-less session

A session saved before roles existed has no role on it. Rather than treat that account as having no permissions, the provider calls fetchProfile() once, writes the answer back to localStorage, and sets state. It is guarded by a stillMounted flag so a late answer cannot set state after unmount.

27.4 logIn and logOut

async function logIn(phone, password) {
  const data = await loginRequest(phone, password);
  const nextUser = { id: data.user_id, username: data.username, role: data.role };
  saveSession(data.tokens.access, nextUser);   // nested. data.access does not exist.
  setUser(nextUser);
  setIsLoggedIn(true);
}

logOut just calls clearSession() and resets both pieces of state. There is no logout endpoint. Discarding the token is all the frontend can do; the token stays valid on the server until it expires. The refresh token from the login response is never stored at all.

Typing "sarah" is six keystrokes. Waiting a moment after the last one turns six requests into one. Two separate state values, not one, is what makes that possible: the input stays responsive while the request lags behind.

setOrdering((current) => (current === field ? `-${field}` : field));

Click a header to sort by it; click the same one again to turn it around. The leading - is what OrderingFilter reads as descending. There is no third "unsorted" state.

  [page, pageSize, search, ordering, filters],
);

Every page lists query.params as a dependency of the effect that loads rows. An object rebuilt on every render would be a new reference every time and the effect would loop forever. This is the single most important line in the file.

if (page > 1 && /invalid page/i.test(problem?.message ?? "")) {

Delete the only row on the last page and the browser is left asking for a page that no longer exists, which the server answers with a 404 saying "Invalid page". Every page's catch block calls this first and bails out if it returns true, so the reader sees the previous page rather than an error.

33.3 Step 2 — the load effect, and the race it avoids

useEffect(() => {
  let isCurrent = true;

  async function load() {
    setIsLoading(true);
    try {
      const body = await teachersApi.list(queryParams);
      if (!isCurrent) return;
      setTeachers(body.results);
      setCount(body.count);
      setTotalPages(body.total_pages);
      setError("");
    } catch (problem) {
      if (!isCurrent) return;
      if (stepBackAfter(problem)) return;
      setError(problem.message);
    } finally {
      if (isCurrent) setIsLoading(false);
    }
  }

  load();
  return () => { isCurrent = false; };
}, [reloadCount, queryParams, stepBackAfter]);

Typing in the search box fires a request per pause, and a slow one can land after a later, quicker one. The isCurrent flag, flipped by the cleanup function, makes the page ignore the answer to a question it has stopped asking. Without it the table can settle on the results for "sara" after you have finished typing "sarah".

35. The authentication lifecycle

35.1 Signing in

POST /api/login/ {"phone": "01700000000", "password": "admin1234"} │ ├─ Profile.objects.get(phone=…) → the User behind it ├─ user.check_password(…) → 400 "Invalid phone or password" if wrong └─ RefreshToken.for_user(user) → {access, refresh} 200 {"message":"Login successful", "user_id":1, "username":"demo_admin", "role":"admin", "tokens":{"access":"eyJ…","refresh":"eyJ…"}} │ AuthContext.logIn(): saveSession(data.tokens.access, {id, username, role}) │ localStorage: lms_access_token = "eyJ…" lms_user = {"id":1,"username":"demo_admin","role":"admin"}

The refresh token is received and thrown away. Nothing in the frontend stores it, because there is nothing to exchange it at.

35.2 While signed in

Every request through request() attaches Authorization: Bearer <access>. The server verifies the signature and the expiry — it does not look the token up in a table, which is the whole point of a JWT and also the whole limitation.

35.3 Signing out, three ways

TriggerWhat happensIs the token really dead?
The Log out buttonclearSession(), state reset, router redirectsNo — it stays valid on the server until it expires

The honest summary: an access token cannot be revoked in this design. Up to eight hours after a password change, a token copied out of localStorage beforehand still works. Shortening ACCESS_TOKEN_LIFETIME and adding a refresh endpoint is the standard fix, and it is the single largest change this project would need before facing anything real.

/forgot-password ──POST /api/password-reset/ {"email": "…"}──► always 200 │ user found? uid = b64(pk), token = default_token_generator │ ◄── email (console backend in dev) ───────────────┘ http://localhost:5180/reset-password?uid=MQ&token=cvx2p1-… /reset-password ──POST /api/password-reset-confirm/ {uid, token, new, confirm}──► decode uid → user, check_token (1 hour window), validate_password, set_password, blacklist refresh tokens ◄── 200 ──── navigate to /login with a notice

36. The list pipeline

Four query parameters, four stages, one envelope. Every list endpoint in the project behaves identically.

GET /api/student/?search=nusrat&is_active=true&ordering=-name&page=2&page_size=25 queryset = Student.objects.all() │ 1 SearchFilter ?search= → OR of icontains over search_fields │ (name, email, roll_number) 2 FieldFilterBackend ?is_active= → declared in filter_fields, coerced to a bool │ 3 OrderingFilter ?ordering= → checked against ordering_fields; "-" = descending │ default ["id"] when absent 4 StandardPagination ?page= → COUNT(*) for the envelope, then LIMIT/OFFSET │ {"count": 214, "page": 2, "page_size": 25, "total_pages": 9, "next": "…?page=3&…", "previous": "…?page=1&…", "results": [ … 25 rows … ]}

36.1 The rules that fall out of that order

  • count is post-filter. It is what the table footer shows and what the dashboard tiles read.
  • Search and filter compose. ?search=nusrat&is_active=true is an AND, not a choice between them.
  • Ordering must be stable or paging breaks. Every view sets ordering = ["id"] as its default; without one, a row can appear on two pages or on neither.
  • An undeclared parameter is silently ignored. ?colour=blue on the students list is not an error — it simply is not on the dictionary.
  • An empty parameter is the same as an absent one. ?course= means "Any", which is why the frontend can send the whole filter object without pruning it first.

38. Performance, and what it cost

Three decisions, each with a number behind it.

38.1 select_related on every joining list view

ResultSerializer reaches submission.student.name and submission.assignment.title. Without select_related, a ten-row page would be 1 query for the results plus 10 for the submissions plus 20 for their students and assignments. With it, one query with joins. The six views that touch relations all declare it.

38.2 Counting without downloading

The dashboard used to fetch all eight tables to display eight numbers — with the current data that is more than 13,000 rows on every visit to the home page. Now:

count: async (params) => {
  const body = await request(`/${path}/${toQueryString({ ...params, page_size: 1 })}`);
  return Array.isArray(body) ? body.length : (body?.count ?? 0);
}

Eight requests, one row each. The count comes from the pagination envelope, which the database was computing anyway.

38.3 Names on the row instead of joins in the browser

Before pagination, the browser downloaded every teacher, course and student and did the id→name join itself. Two things broke that. A page of ten rows should not cost eight thousand. And once the lookup lists were paginated too, a lookup list cannot answer for a row on page 40 — the name simply would not be there. Sending teacher_name alongside teacher costs nothing, because the join is already in the queryset.

What is still fetched in full: the dropdown lists, via listAll(). Those are 26 teachers, 24 courses, 180 students and 180 assignments — small, and needed whole because a <select> cannot page.

38.4 ?ungraded=true

The Results page needs the submissions nobody has marked. Computing that in the browser means downloading 7,665 submissions and 4,630 results and subtracting one set from the other. As a query it is results__isnull=True, and the page asks for the first 200 of them.

38.5 The debounce

300 ms after the last keystroke, not on every one. Typing a six-letter name is one request instead of six — and the isCurrent flag means that even if two are in flight, the older answer cannot overwrite the newer one.

45. Rough edges and known gaps

An honest inventory. None of these stop the app working; all of them are worth knowing before you build on it.

45.1 Structural

GapConsequence
Nothing links Student to UserThe server cannot tell whose submission is whose. Hence the odd submission permission, and hence a student being able to POST a submission naming somebody else as its author.
No unique constraint on EnrollmentThe same student can be enrolled on the same course twice. A unique_together would fix it.
Assignment has both a course and a lessonNothing checks that the lesson belongs to the course. The UI narrows the dropdown; the API does not care.
No Meta.ordering on any modelHarmless — every list view sets ordering explicitly — but a queryset used anywhere else has no defined order.
Teacher/Student rows and login accounts are joined by email convention onlyDeleting one leaves the other. The seeder maintains the convention; nothing enforces it.

45.2 Authentication

GapConsequence
No token refresh endpointThe refresh token is issued, handed over and discarded. The access token is widened to 8 hours to compensate.
No logout endpointLogging out is client-side only. The token stays valid until it expires.
Access tokens cannot be revokedA password change blacklists refresh tokens only. See chapter 35.
A superuser cannot use the app's login pageNo Profile, so no phone number to sign in with. /admin/ only.
No rate limiting anywhere/login/ can be hammered.

45.3 Testing and tooling

GapConsequence
tests.py is emptyNo unit tests. The smoke test is thorough but needs a running server and a seeded database, so it cannot run in a clean CI job unaided.
requests is not in requirements.txtThe smoke test's only dependency is undeclared.
No frontend testsnpm run build and the screenshot script are the whole safety net.
no-unused-vars ignores capitalised namesA genuinely unused component import is never reported.
No CI configurationNothing runs the lint or the smoke test automatically.

45.4 Small inconsistencies

  • DEMO_ACCOUNTS is duplicated in seed_data.py and Login.jsx, and the two have drifted — the login page offers only the admin.
  • /submission/ is singular, /results/ is plural.
  • The model is Results (plural) but the serializer is ResultSerializer (singular).
  • The detail views have no select_related while their list views do.
  • backend/backend/urls.py gives names to the resource routes but the two password-reset paths have none.
  • blacklist_user_tokens() swallows every exception silently, so a broken blacklist app would never be noticed.
  • The frontend never uses PATCH for resources — always PUT with the full row — even though the API supports both.
  • There is a frontend/dist/ directory on disk from an earlier build; it is gitignored and not tracked.

None of the above is a bug in the sense of "this does not work". They are the places where the next person will be surprised, which is what this chapter is for.
